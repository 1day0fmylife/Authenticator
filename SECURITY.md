# Security Policy

**Статус:** Draft v0.1, 15.11.2026.
**Область:** desktop Authenticator (Rust), Go MFA verifier, общие OTP-компоненты, сборочная цепочка и релизные артефакты.

## Как сообщить об уязвимости

**Не создавайте публичный GitHub issue и не публикуйте детали до согласования.**

Используйте **GitHub Private Vulnerability Reporting**, если он включён для репозитория (вкладка *Security → Advisories → Report a vulnerability*):

```text
https://github.com/1day0fmylife/Authenticator/security/advisories/new
```

Если приватный канал недоступен, создайте минимальный публичный issue **без деталей эксплуатации** с просьбой открыть приватный канал связи. Включение Private Vulnerability Reporting входит в release-hardening.

Отдельного PGP-ключа и публичного e-mail на текущий момент нет; это ограничение будет снято до стабильного релиза.

## Что включить в отчёт

1. Компонент и версия/коммит (desktop, verifier, сборка, зависимости).
2. Платформа (Windows/Ubuntu, версия; для сервера — окружение PostgreSQL).
3. Краткое описание уязвимости и затронутый актив (vault, seed, OTP, tenant isolation, recovery, supply chain).
4. Воспроизводимые шаги или PoC **с синтетическими данными**.
5. Оценка impact и условий эксплуатации (локально/удалённо, нужна ли аутентификация).
6. Известные ограничения и предложения по исправлению (если есть).

**Запрещено присылать:** реальные TOTP seeds, OTP, recovery codes, пароли, ключи шифрования/подписи, содержимое чужих vault/БД, персональные данные. Для демонстрации используйте сгенерированные тестовые значения и сразу помечайте их как тестовые.

## Наши обязательства

- Подтвердить получение в течение **3 рабочих дней**.
- Провести первичный triage и сообщить предварительную оценку в течение **10 рабочих дней**.
- Согласовать срок исправления и раскрытия; по умолчанию — исправление до публикации деталей.
- Указать исследователя в advisory, если он этого хочет.
- Не предпринимать юридических действий против добросовестных исследований в рамках этой политики; не выходить за пределы тестовых данных и своих систем.

Bug bounty и денежные вознаграждения сейчас **не предусмотрены**. Это не уменьшает важность отчётов.

## Приоритеты

| Severity | Примеры |
| --- | --- |
| Critical | Раскрытие seed/ключей, обход MFA, cross-tenant доступ, подмена релизного артефакта, fail-open |
| High | Replay OTP, кража vault с последующим подбором пароля, RCE через импорт/парсер, компрометация service identity |
| Medium | Ограниченная утечка метаданных, DoS, обход rate limit без доступа к данным |
| Low | Ошибки UX/диагностики без раскрытия секретов, незначительные hardening-замечания |

## Вне области

- Компрометация ОС/kernel/malware с правами пользователя или выше; физический доступ к разблокированной машине.
- Фишинг и real-time relay TOTP-кодов: TOTP **не является** phishing-resistant по дизайну.
- Атаки на сторонние сервисы, использующие коды, и на relying party после успешной проверки.
- Ошибки в зависимостях без достижимого влияния на наш код (присылайте, но приоритет ниже).
- Социальная инженерия, спам, отчёты сканеров без воспроизведения.
- Отсутствие функций, запланированных в P1/P2/P3.

## Координация раскрытия

- По умолчанию: приватное исправление → релиз с исправлением → публикация advisory с ограниченными техническими деталями.
- Если уязвимость уже эксплуатируется, допускается ускоренное раскрытие после выпуска исправления.
- Мы не публикуем рабочие эксплойты, реальные секреты и данные пользователей.

## Ограничение текущего статуса

Проект находится на стадии архитектуры: production-релизов нет. Отчёты всё равно принимаются — особенно по дизайну vault/verifier и по supply-chain политике.
