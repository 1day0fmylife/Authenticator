# ADR-001 — Независимость desktop и MFA verifier, стандарты RFC 4226/6238 и модель ответственности

- **Статус:** Accepted (v0.1)
- **Дата:** 15.11.2026
- **Задача:** TODO `ADR-001`
- **Контекст:** PLAN §1–§4; README «Граница безопасности»; SEC-001 threat model; SEC-002 supply-chain.
- **Решение фиксирует уже заявленные в README/PLAN принципы** и не выбирает GUI framework, crypto crates или формат vault — это ADR-002…ADR-005.

## 1. Контекст

Проект состоит из двух **независимых** продуктов с разными trust boundaries:

1. **Desktop Authenticator (Rust, Windows/Ubuntu)** — локальная offline-генерация TOTP/HOTP, зашифрованный переносимый vault.
2. **Go MFA Verifier** — server-to-server сервис проверки второго фактора для существующих backend-приложений.

Исторически OTP-экосистемы часто смешивают генератор, облачную синхронизацию и сервер проверки, что создаёт vendor lock-in, лишние сетевые зависимости и неверную модель ответственности («приложение считает пользователя аутентифицированным»). Для проекта это неприемлемо: desktop должен работать при полностью недоступной сети/инфраструктуре, а verifier — принимать коды любого совместимого клиента.

## 2. Решение

### 2.1. Rust-first desktop

- Core-логика (`otp-core`, `vault`, `app-core`) реализуется на **safe Rust** в отдельном workspace; GUI — отдельный crate (`app-gui`) за абстракциями, выбор framework — ADR-002.
- Desktop **не** содержит обязательного C++/Qt/Electron/Node/WebEngine runtime и **не** требует FFI для криптографии/хранилища.
- GUI не влияет на OTP-векторы, формат vault и API-контракты.

### 2.2. Отсутствие runtime-зависимости между компонентами

| Направление | Разрешено | Запрещено |
| --- | --- | --- |
| Desktop → Verifier | ничего; desktop не знает о существовании verifier | сетевые вызовы, регистрация, синхронизация, лицензионная проверка |
| Verifier → Desktop | ничего | зависимость от нашего клиента, proprietary enrollment |
| Desktop → внешний сервис | только если пользователь сам вводит код в стороннем сервисе | автоматическая отправка кодов, скрытые network-функции |
| Verifier → внешний backend | документированный server-to-server API | браузерный tenant, доверие клиентскому флагу MFA |

Следствия:

- Desktop генерирует корректные RFC-коды **без** нашего сервера, аккаунта, интернета и обновлений.
- Verifier проверяет коды **любого** TOTP-клиента (Google Authenticator, Aegis, 1Password и т.п.); наш desktop — с **любым** RFC-совместимым сервером/сервисом.
- Vault не синхронизируется через verifier; verifier не получает клиентские seeds и не является backup-сервисом.

### 2.3. Стандарты и совместимость

Обязательный общий контракт:

- **HOTP:** RFC 4226, counter-based.
- **TOTP:** RFC 6238, time-based.
- **URI:** `otpauth://totp|hotp/...` с issuer/account, algorithm, digits, period/counter.
- **Алгоритмы:** SHA-1 (для совместимости), SHA-256, SHA-512.
- **Digits:** 6 и 8. **Period:** 30 с по умолчанию; иные значения — только при валидной поддержке в обеих реализациях.
- **Векторы:** единые публичные RFC test vectors в `tests/vectors/` для Rust и Go (OTP-001), плюс независимая проверка.
- **Parser:** строгий, с лимитами длины/полей и отказом на противоречиях/неподдерживаемых параметрах (OTP-004).
- **Секреты:** seed/OTP/QR/URI с секретом не логируются и не попадают в фикстуры с реальными данными.

Общие тест-векторы — часть контракта, а не деталь реализации: расхождение Rust/Go на одних и тех же входах блокирует релиз.

### 2.4. Модель ответственности

| Сторона | Отвечает | НЕ отвечает |
| --- | --- | --- |
| **Пользователь** | сохранность пароля vault, выбор устройства | корректность серверной сессии |
| **Desktop Authenticator** | локальная генерация, шифрование vault, целостность локального файла | primary authentication, серверная сессия, защита скомпрометированной ОС |
| **Relying party backend** | primary auth, RBAC/ABAC, создание/повышение **своей** сессии, проверка решения MFA | хранение OTP-секретов (делегируется verifier) |
| **MFA Verifier** | enrollment, challenge, verify, replay/rate-limit, tenant isolation, шифрование seeds at rest | объявление пользователя аутентифицированным, primary session, замена IdP |
| **Оператор** | внешние ключи, TLS/mTLS, конфигурация, мониторинг, fail-closed | безопасность клиентских устройств |

Ключевые инварианты:

1. Успешный `verify` возвращает **решение** relying party; сессию создаёт/повышает только backend приложения.
2. Verifier **не** принимает tenant/subject как источник авторизации от браузера; tenant определяется аутентифицированной service identity.
3. Ошибка/недоступность verifier — **fail closed** для MFA-шага; никакого «пропустить, если сервис недоступен».
4. TOTP **не является** phishing-resistant; UI/документация не должны намекать на обратное.
5. Desktop не становится доверенным просто потому, что он «наш»; verifier не доверяет данным клиента без server-to-server identity.

### 2.5. Границы форматов

- Формат vault (**ADR-004**) — локальный, версионированный, не является API и не диктует серверную схему.
- API verifier (**ADR-005**) — только server-to-server JSON/HTTPS; не содержит полей вида `vault`, `desktop_device_id`, `client_version` как обязательных.
- OpenAPI не зависит от GUI/desktop-реализации; примеры FastAPI/Go — потребители контракта, а не его владельцы.

## 3. Последствия

### Положительные

- Desktop сохраняет работоспособность в изолированной сети и при отказе серверной инфраструктуры.
- Пользователь не привязан к нашему серверу; сервис не привязан к нашему клиенту.
- Ответственность за сессию остаётся у relying party — снижается риск неверной интеграции.
- Общие RFC-векторы дают объективную проверку совместимости.

### Отрицательные / издержки

- Нет «удобной» синхронизации vault и восстановления через аккаунт — это осознанно отложено (P2, отдельный продукт).
- Нет единого UX «одним продуктом»: desktop и verifier развиваются раздельно.
- Требуется поддерживать строгий URI parser и несколько алгоритмов/digits.
- Интеграторам нужно явно реализовать primary auth и проверку решения MFA; примеры обязательны (INT-001/INT-002).

### Риски

| Риск | Смягчение |
| --- | --- |
| Интегратор объявит сессию authenticated по одному факту успешного verify без привязки к своей сессии | Контракт, sequence diagrams, негативные тесты, явная документация (ADR-005) |
| Пользователь потеряет пароль vault и решит, что сервер восстановит данные | Явный UX, переносимый backup, документация (VAULT-005) |
| Расхождение реализаций Rust/Go | Общие векторы + property/fuzz тесты (OTP-001…003) |
| Появление скрытой сетевой функции в desktop | Dependency/network review, offline build, тест с запрещённой сетью (SUP-002) |

## 4. Альтернативы

| Альтернатива | Причина отказа |
| --- | --- |
| Единый облачный authenticator с аккаунтом | Vendor lock-in, сетевая зависимость, расширение TCB, противоречит offline-first |
| Форк Ente/чужого клиента | Наследует чужие решения/лицензии/форматы, не даёт независимости |
| Синхронизация vault через verifier | Смешивает продукты и активы, увеличивает impact серверной компрометации |
| Proprietary enrollment/OTP | Нарушает совместимость и стандартность |
| C++/Qt как основа | Не нужен для core, расширяет unsafe/FFI и native supply chain; Rust-first безопаснее для памяти |
| Verifier «подтверждает сессию» браузера напрямую | Ломает trust boundary; tenant/session должны принадлежать backend |

## 5. Критерии соответствия (проверяемые)

- [ ] В workspace нет зависимости desktop-крейтов от HTTP/сетевых библиотек; `cargo tree` это подтверждает.
- [ ] Desktop собирается и генерирует коды в окружении без сети.
- [ ] `tests/vectors/` используются и Rust, и Go; расхождение — fail.
- [ ] В `api/openapi.yaml` нет desktop-specific обязательных полей; tenant не принимается из пользовательского ввода (contract tests).
- [ ] Успешный verify не создаёт сессию; примеры показывают проверку решения relying party (INT-001/INT-002).
- [ ] Документация явно указывает: TOTP не phishing-resistant, compromised OS не защищается.
- [ ] Verifier outage приводит к отказу MFA-шага, не к bypass.

До выполнения этих пунктов ADR остаётся **Accepted как архитектурное решение**, но соответствующие TODO не считаются завершёнными.

## 6. Что этот ADR не решает

- GUI framework (ADR-002), crypto crates/AEAD/KDF (ADR-003), vault format (ADR-004), verifier API/identity/replay scheme (ADR-005).
- Мобильные клиенты (P3), WebAuthn (P2), E2EE sync (P2).
- Лицензия проекта и модель управления (PLAN §7).
