# ADR-003 — RustCrypto crates, AEAD, Argon2id и ключевой envelope

- **Статус:** Accepted (v1.0)
- **Дата:** 15.11.2026
- **Задача:** TODO `ADR-003`
- **Связанные:** [SEC-001 threat model](../threat-model.md), [SEC-002 supply-chain](../supply-chain.md), [ADR-001](0001-independence.md); формат файла — ADR-004, контракт сервера — ADR-005.
- **Область:** desktop Rust (`otp-core`, `vault`). Go verifier использует stdlib и не зависит от этого ADR.

## 1. Решение

1. **OTP:** `hmac` + `sha1`/`sha2` (RustCrypto), constant-time сравнение через `subtle`.
2. **KDF:** Argon2id (RFC 9106), версия `0x13`, `m=64 MiB`, `t=3`, `p=1`, output 32 байта, salt 16 байт.
3. **AEAD vault:** **XChaCha20-Poly1305** (192-bit nonce), 24-байтный случайный nonce, 16-байтный tag, AAD = канонический заголовок файла.
4. **Ключевой envelope v1:** `password (UTF-8) → Argon2id(salt, m, t, p, 32) = vault_key`; `vault_key` напрямую используется как ключ XChaCha20-Poly1305. Отдельный key-wrap/HKDF в v1 не вводится; `key_id` зарезервирован для будущей ротации.
5. **Секреты:** пароль не сохраняется; `vault_key` живёт только в памяти в `zeroize`-контейнере; seed/ключи/OTP не логируются; новые salt/nonce — только из ОС CSPRNG; ошибка CSPRNG = отказ.
6. **Тестовые векторы:** RFC 4231 (HMAC-SHA-256), RFC 9106 (Argon2id), draft-irtf-cfrg-xchacha (XChaCha20-Poly1305), общие RFC 4226/6238 из `tests/vectors/`.

## 3. AEAD: XChaCha20-Poly1305

**Выбрано:** XChaCha20-Poly1305 (RFC 8439 ChaCha20-Poly1305 с 192-битным nonce).

Причины:

- 24-байтный случайный nonce: collision resistance ~2^96 даже при большом числе перезаписей одним ключом; не требует счётчика/состояния между запусками.
- Не зависит от AES-NI/аппаратного ускорения; одинаковое поведение на Windows/Ubuntu и старых CPU.
- Pure-Rust реализация без FFI; в `chacha20poly1305` нет `unsafe`-файлов.
- Один AEAD-примитив для payload; key-wrap не нужен, пока ключ один.

**Отклонено:** AES-256-GCM — безопасен, но 96-битный nonce повышает цену ошибки/коллизии при случайной генерации и качество зависит от аппаратной реализации; для offline-файла без счётчика XChaCha проще корректно эксплуатировать. Это не утверждение, что AES-GCM небезопасен.

Параметры: key 32 байта, nonce 24 байта, tag 16 байт; nonce хранится в заголовке открыто и аутентифицируется как AAD. Nonce **не** выводится из пароля/времени; только CSPRNG.

## 4. Argon2id

| Параметр | Значение |
| --- | --- |
| Algorithm | Argon2id |
| Version | `0x13` (19) |
| Memory (`m`) | 64 MiB (65536 KiB) |
| Iterations (`t`) | 3 |
| Parallelism (`p`) | 1 |
| Output | 32 байта |
| Salt | 16 байт, CSPRNG, уникальный на файл/backup |
| Secret / AD | не используются в v1 (совместимость с переносимым форматом) |

**Допустимые границы при чтении файла:** `m` 19 MiB…256 MiB, `t` 2…6, `p` 1…4, salt ровно 16 байт. Значения вне границ — ошибка формата, не «попробуем всё равно». Это защита от hostile-файла, задающего неограниченную стоимость KDF.

**Измерение** (Linux x86_64, release, текущая машина разработки; не является обещанием для всех систем):

| Параметры | Время |
| --- | --- |
| 19 MiB, t=2, p=1 | ~25 мс |
| 64 MiB, t=2, p=1 | ~90 мс |
| 64 MiB, t=3, p=1 | ~121 мс |
| 256 MiB, t=3, p=1 | ~509 мс |

UI обязан показывать прогресс/занятость при unlock; целевое время на референсном оборудовании — до ~500 мс. Параметры хранятся в заголовке и проверяются по границам; автоматическая «калибровка» без согласия пользователя не меняет формат.

Пароль: UTF-8 байты введённой строки, **без Unicode-нормализации** в v1 (смена нормализации сделает существующие vault недоступными); при создании/смене — 12…1024 байт, при открытии — 1…1024 байт, чтобы смена UX-политики не блокировала старый файл. Минимальная длина — UX-политика, а не замена энтропии.

## 5. Ключевой envelope v1

Концептуально (точная бинарная раскладка — ADR-004):

```text
header (открытый, аутентифицируется как AAD):
  magic, format_version, kdf_id, m_cost, t_cost, p_cost,
  key_id (=0 в v1), salt[16], nonce[24]
ciphertext+tag = XChaCha20Poly1305(
  key   = Argon2id(password, salt, m_cost, t_cost, p_cost, 32),
  nonce = nonce,
  aad   = canonical_header_bytes,
  plaintext = serialized vault payload
)
```

Инварианты:

1. **AAD покрывает весь заголовок** (включая версию, KDF-параметры, salt, nonce, key_id). Любая модификация заголовка → ошибка аутентификации.
2. **Один ключ — много nonce, nonce не повторяется.** При каждой записи генерируется новый 24-байтный nonce; salt/key меняются только при смене пароля/KDF или явном re-encrypt export. Обычное сохранение переиспользует ключ с новым nonce.
3. **Backup/export.** Побайтовая копия файла — допустимый backup (тот же salt/key/nonce). Явный export с новым паролем создаёт новый salt, новый ключ и новый nonce; это не «перешифрование» старой копии.
4. **key_id = 0** в v1; поле зарезервировано для будущей ротации. Неизвестный `key_id` → fail closed.
5. **Ошибка RNG, аутентификации, KDF или записи** → операция отменяется; повреждённый/нечитаемый файл никогда не заменяется пустым vault.
6. Пароль и ключ не попадают в `Debug`, логи, ошибки, panic-сообщения, телеметрию и имена файлов.

`zeroize` применяется к `vault_key`, буферам пароля и расшифрованного payload там, где время жизни контролируется. Гарантировать стирание копий ОС/swap/драйверов нельзя — это остаточный риск R-7.

### 5.1. Trust boundaries и негативные сценарии

Доверенная граница: код `vault` и ОС CSPRNG. Недоверенные данные: содержимое файла, введённый пароль, импортируемый backup. Заголовок читается как hostile input.

| Сценарий | Обязательное поведение |
| --- | --- |
| Неверный пароль | Ошибка аутентификации; файл не изменяется; пустой vault не создаётся |
| Изменён header/ciphertext/tag | AEAD-ошибка; отказ без частичной расшифровки и без записи |
| Truncated/oversized файл, неизвестная `format_version`/`kdf_id`/`key_id` | Ошибка формата до дорогого KDF или до расшифровки; fail closed |
| Hostile KDF-параметры вне §4 | Отказ до выделения памяти/вычисления Argon2id |
| Ошибка CSPRNG | Операция отменяется; nonce/salt не заменяются предсказуемыми значениями |
| Сбой записи/fsync/rename | Старый файл сохраняется; новый считается отсутствующим (детали — ADR-004) |
| Rollback на старую аутентичную копию | **Не обнаруживается** без внешнего доверенного состояния; остаточный риск, не обещается защита |

## 6. Проверенные test vectors

| Примитив | Вектор | Результат |
| --- | --- | --- |
| HMAC-SHA-256 | RFC 4231 case 2 (`Jefe`) | OK |
| Argon2id | RFC 9106 §5.3 (secret + associated data, m=32 KiB, t=3, p=4) | OK |
| XChaCha20-Poly1305 | draft-irtf-cfrg-xchacha-03 §A.3.1 | OK |
| HOTP/TOTP | 71 общий вектор RFC 4226/6238 | OK (Go core и Rust `otp-core`) |

Проверка Argon2id/XChaCha/HMAC выполнена отдельной probe-программой на тех же pinned-версиях. Rust `otp-core` прогоняет все 71 общий вектор (RFC 4226 counters 0…9, RFC 6238 SHA-1/256/512, 6/8 digits, границы времени, period 60) и property-тесты HOTP/TOTP-эквивалентности. Argon2id-вектор использует secret+AD через `Argon2::new_with_secret` и `ParamsBuilder::data`, что подтверждает корректность низкоуровневого API.

## 7. Dependency / license / unsafe assessment

- Полный граф планируемого crypto-стека: **28** пакетов (normal+build, Linux x86_64, без dev); с dev-зависимостями — **33**. Для `otp-core` отдельно: **13** normal+build (прямых 5), с dev — 18. Это в рамках уточнённого бюджета SEC-002 (`otp-core` ≤5 прямых / ≤13 транзитивных, полный стек ≤40).
- Лицензии всех пакетов — MIT / Apache-2.0 / BSD-3-Clause / ISC-совместимые. Встречаются dual-license варианты: `r-efi` (MIT OR Apache-2.0 OR LGPL-2.1-or-later — используется permissive-вариант), `ryu` (Apache-2.0 OR BSL-1.0), `memchr` (Unlicense OR MIT). GPL/AGPL/SSPL/BUSL в обязательном графе нет.
- `build.rs` в нормальном графе: `generic-array` (проверка версии rustc), `getrandom` (cfg/version, вызов rustc wrapper), `libc` (cfg; `freebsd-version`/`emcc` только на соответствующих target). Сети, скачивания кода и записи в исходники нет. Dev-only: `serde_json` (выбор limb width по target).
- `unsafe`: отсутствует в нашем коде; в зависимостях сосредоточен в CPU-intrinsics/FFI/volatile-операциях (`sha1`, `sha2`, `getrandom`, `libc`, `zeroize`, `subtle`). Это **не** построчный аудит зависимостей; выполнена проверка назначения, версии и графа. Полный review — SEC-002/SUP-004.
- `chacha20poly1305` и `argon2` не имеют `build.rs`; `chacha20poly1305` — 0 unsafe-файлов.
- Транзитивные версии зафиксированы `Cargo.lock`; offline/vendor сборка — SUP-002, здесь не заявляется.

## 8. Альтернативы

| Альтернатива | Причина отказа |
| --- | --- |
| AES-256-GCM | 96-битный nonce и зависимость от аппаратной реализации; допустимая будущая альтернатива через ADR |
| ChaCha20-Poly1305 (96-bit nonce) | Меньше пространство nonce при случайной генерации |
| scrypt / PBKDF2 | Argon2id рекомендован RFC 9106/OWASP; PBKDF2 слабее против GPU/ASIC |
| `ring` / OpenSSL / libsodium FFI | Native/FFI и платформенные различия; увеличивает TCB и сложность offline build |
| Самодельный KDF/AEAD | Прямо запрещено AGENTS |
| PHC-string (`password-hash`) как формат vault | Дублирует собственный версионированный формат; строка не задаёт AAD/структуру payload |
| HKDF/key-wrap в v1 | Один ключ и один payload; дополнительная схема не даёт выгоды без ротации/нескольких получателей |

## 9. Последствия и остаточные риски

- Unlock стоит ~120 мс CPU и 64 MiB памяти; на слабых устройствах дольше. Это осознанная цена offline-защиты.
- Слабый пароль остаётся главным риском (R-2): Argon2id повышает стоимость подбора, но не создаёт энтропию.
- Random nonce безопасен только при корректном CSPRNG; ошибка RNG должна быть фатальной, а не «продолжить с нулями».
- Компрометация ОС/памяти не предотвращается (R-1); `zeroize` — best-effort.
- Отсутствие HKDF означает, что при будущем разделении ключей (payload/backup/index) потребуется новая версия формата/ADR; v1 это допускает через `format_version`/`key_id`.
- Откат файла к более старой, но аутентичной версии не детектируется без внешнего доверенного счётчика/реестра. Это осознанно вне scope v1.
- Выбранные minor-версии не самые новые; обновление — контролируемый процесс, а не автоматический.

## 10. Реализация и проверки

Реализовано в рамках OTP-002:

- `desktop/crates/otp-core` использует `hmac`, `sha1`, `sha2`, `subtle`, `zeroize`; `#![forbid(unsafe_code)]`; общие векторы читаются из `tests/vectors/`.
- Проверки (фактически выполнены, Linux x86_64, Rust 1.91.0): `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --locked` (15 тестов), `cargo tree --locked` (13 пакетов normal+build), `cargo build --workspace --release --locked --frozen`.
- `VAULT-002…005` используют параметры и envelope из §4–§5; точная бинарная раскладка — ADR-004 (до кода).
- Обязательные проверки для vault: negative-тесты nonce/AAD/tamper/wrong-password, crash consistency, backup restore; отдельно — независимый security review.
- Этот ADR **не** означает, что vault готов или прошёл независимый security review (QA-002).
