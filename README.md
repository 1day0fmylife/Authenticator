# Authenticator

**Статус:** проектирование архитектуры; исходный код и релизы пока отсутствуют.

Authenticator — независимый, ориентированный на безопасность набор из **локального десктопного TOTP/HOTP-клиента** (Windows и Ubuntu) и **отдельного серверного MFA-verifier** для интеграции с собственными сервисами. Ни клиент, ни сервер не зависят от Ente Auth, Authy, Keycloak или иных конкретных продуктов. **Мобильные клиенты отложены** до стабилизации десктопа и сервера.

## Принципы

1. **Стандартные протоколы и переносимость:** RFC 4226 (HOTP), RFC 6238 (TOTP), `otpauth://`; совместимость со сторонними Authenticator-приложениями. Никаких проприетарных обязательных протоколов.
2. **Offline-first:** генерация кодов на десктопе не требует аккаунта, сервера, сети, DNS, push или телеметрии.
3. **Минимальная доверенная кодовая база (TCB):** минимум фреймворков, сторонних пакетов, плагинов, runtime и способов исполнения кода. Не разрабатывать собственные криптографические примитивы.
4. **Контроль цепочки поставок:** фиксировать версии/хеши, вести SBOM, поддерживать офлайн-сборку, аудировать транзитивные зависимости, подписывать релизы.
5. **Разделение доверия:** десктопный vault хранит пользовательские OTP-секреты локально; MFA-verifier хранит серверные enrollment-секреты зарегистрированных пользователей и никогда не нуждается в доступе к десктопному vault.
6. **Нет зависимости от одного IAM:** корпоративные приложения остаются ответственными за primary authentication, сессии и авторизацию; MFA — отдельно подключаемый фактор.

## Приоритеты и стек

| Направление | Приоритет | Стек (архитектурное решение) |
| --- | --- | --- |
| Десктоп Windows 10/11 и Ubuntu LTS | **P0** | C++20, Qt 6 **Widgets** (без WebEngine/QML/JS), CMake, OpenSSL 3, SQLite |
| MFA-verifier для проектов | **P0** | Go, `net/http`, PostgreSQL, минимальный проверенный драйвер БД |
| Интеграционные адаптеры | P1 | HTTP/OpenAPI; тонкие примеры на Python/FastAPI и Go, без обязательного SDK |
| Шифрованные резервные копии и перенос | P1 | Документированный версионированный формат, AEAD, тесты совместимости |
| Синхронизация vault между устройствами | P2, отдельно | Только после threat model и протокола E2EE; не обязательна для MFA |
| WebAuthn/FIDO2 | P2 | Отдельный RFC/ADR; предпочтителен для фишинг-устойчивой аутентификации |
| Android / iOS | **P3** | Не начинать до стабильного десктопа и сервера; позднее нативные клиенты |

**Выбор Qt Widgets:** один desktop GUI toolkit для двух ОС; без браузерного движка, Node.js, Electron, React Native или Flutter. Это не означает «нулевые зависимости»: Qt, OpenSSL и SQLite входят в TCB и подлежат учёту. Пересмотр допускается лишь по измеримому dependency/TCB audit и ADR.

## Границы системы

```text
Windows / Ubuntu                             Внутренние сервисы
+--------------------------------+          +-----------------------------+
| Authenticator Desktop (offline)|          | FastAPI / Go / другое       |
| UI (Qt Widgets)                 |          | primary auth + session     |
| Vault (AEAD / SQLite)           |          +--------------+--------------+
| OTP RFC4226/6238                |                         |
| OS protection: DPAPI /          |               trusted HTTPS/mTLS
| Secret Service + passphrase     |                         |
+----------------+---------------+          +--------------v--------------+
                 |                          | Go MFA verifier API          |
       otpauth:// / QR / manual            | enroll / challenge / verify |
                 |                          | rate-limit / replay guard   |
                 +-- standard OTP code --> | PostgreSQL + encrypted keys |
                             (via relying app)+-----------------------------+
```

Десктоп **не вызывает** MFA-verifier для вычисления кодов и способен использоваться с любым сервисом, поддерживающим RFC TOTP/HOTP. Версионная проверка состояния vault и резервного восстановления обязательна.

## Безопасность

- **Threat model:** в границах проекта — кража файла vault, компрометация базы MFA, replay TOTP, подмена сервера, вредоносные обновления, ошибки импорта и rollback. Вне гарантий — произвольное выполнение кода с правами разблокированного пользователя и полностью скомпрометированная ОС.
- **Vault:** все секреты и чувствительные поля шифруются аутентифицированным алгоритмом (план: AES-256-GCM); случайный ключ данных, уникальные nonce; версионированный формат и AAD; атомарные обновления и восстановление после сбоев.
- **Защита ключей:** Windows DPAPI (current-user); Ubuntu Secret Service *при наличии*; обязательный fallback через парольную KDF (план: scrypt/OpenSSL 3) с тестируемыми параметрами. Утрата keyring не должна silently очищать vault.
- **MFA server:** строгая граница доверия; enrollment только после primary auth и step-up; шифрование секретов в БД с отдельным от БД ключом; одноразовые recovery codes в виде стойких хешей; атомарная защита от повторного использования одного TOTP time-step; ограничение попыток. Tenant/project ID определяется доверенными учётными данными вызывающего сервиса, не параметрами клиента.
- **Коды:** поддерживать SHA-1 для совместимости с RFC TOTP (это не применение SHA-1 для цифровой подписи), опционально SHA-256/512; проверять предсказуемое окно дрейфа времени, не допускать повторного принятия кода.
- **Без облачной зависимости:** никакой автоотправки секретов, аналитики, сетевого разрешения зависимостей при runtime; в логах нет OTP, seed, паролей, recovery codes или QR payload.
- **Не обещать абсолютной защиты:** защита ключей ОС не спасает от кода, исполняемого с полномочиями разблокированного пользователя.

## Минимальный контракт интеграции (проектируемый, пока НЕ реализован)

Рассматривается сервисный API `/v1/mfa` с этапами `enrollment/start`, `enrollment/confirm`, `challenges`, `challenges/{id}/verify` и управляемым отключением фактора. Конкретные методы, payload, OAuth/OIDC-интеграции, TTL и модель авторизации будут зафиксированы в OpenAPI до написания обработчиков.

**Поток:** проект выполняет primary authentication → его доверенный backend создаёт привязанный к пользователю/сессии MFA challenge → пользователь вводит TOTP в исходном проекте → backend обращается к verifier → только backend проекта повышает уровень аутентификации сессии. Браузер не может объявлять пользователя «прошедшим MFA», а verifier не принимает недоверенный user ID/tenant из публичного запроса.
